## 00 — Framing

The risk with this project isn't getting a model to imitate the scratchpad shape — any 7B instruct model will mimic bracketed headers after a dozen examples. The risk is training it to *always* dump the full scaffold regardless of whether the task earns it, which is the exact failure mode the skill's own "trigger aggressively, not optional" language invites. A dataset that only contains full-scaffold examples teaches reflex, not judgment.

So the dataset's job is to teach **when** as much as **how**: trivial questions get a thin response, ambiguous ones get real clarification, high-stakes ones get the conditional tags, and none of it is decoration bolted onto an otherwise-unchanged answer.

## 01 — Task Taxonomy

Every example is generated by picking one value from each axis below. The full cross-product is the space you're sampling from — you don't need every cell, but you need enough spread that "always fire everything" stops being a winning strategy for the model to learn.

| Axis | Values | What it stresses |
|------|--------|------------------|
| **Domain** | general reasoning · dev/CLI · research & citation · persona/creative · ethics-adjacent · ops/planning | vocabulary, which CTL tags are even plausible |
| **Complexity tier** | trivial · moderate (MVS) · complex (extended tags) · high-stakes (full stack) | restraint — does the model scale effort to the task |
| **Context load** | zero-context single turn · multi-turn with prior state · tool-augmented · long-document grounding | whether ContextIntegration / ToolsUsed carry real content or filler |
| **Verifiability** | closed-form (math/code/fact) · open, rubric-graded | lets you grade substance, not just structure |

### Trivial tier is not optional

Deliberately include a slice — 15–20% of the set — where the ideal response is short and the scaffold is nearly empty. "What's 12% of 340?" does not need a Theory of Mind section. If every training example has a full scratchpad, restraint is un-learnable; the model has literally never seen a case where firing less was correct.

## 02 — What Makes an Example High-Fidelity

Four gates, and an example only earns a place in the training set if it clears all four — not just structurally valid, which is the low bar most synthetic scratchpad data stops at.

1. **Structurally correct.** Fence order, section presence, blank-line rules — parseable by a script, not a judge call.
2. **Substantively correct.** The final answer is actually right (verifiable tier) or clears a written rubric (open tier). A beautifully formatted wrong answer is a negative example, not a positive one.
3. **Non-vacuous sections.** Each fired section contains a claim specific to *this* task — reject/regenerate any example where a section could be copy-pasted onto an unrelated question unchanged.
4. **Calibrated firing.** The CTL tags that fired are the ones the task's own complexity tier predicts, and — just as important — the ones that *didn't* fire are recorded as a deliberate negative signal.

> That fourth gate is the one worth building tooling around first. Everything else is a format checker; this is the difference between a model that reasons and one that performs reasoning-shaped text.

## 03 — Context Schema

One row, one example. `prior_context` and `expected_ctl` are the two fields most synthetic-data pipelines skip, and they're the two that make this dataset different from "a thousand scratchpad completions."

| Field | Type | Description |
|-------|------|-------------|
| `task_id` | string | stable slug, e.g. `dev-moderate-toolaug-014` |
| `domain` | enum | general · dev-cli · research · persona · ethics · ops |
| `complexity_tier` | enum | trivial · moderate · complex · high-stakes |
| `context_load` | enum | none · multi-turn · tool-augmented · long-doc |
| `prompt` | string | the raw user turn |
| `prior_context` | string \| null | conversation history / file / tool output the ideal response must actually reference |
| `target_variant` | enum | which skill spec applies: bifurcated-MVS · three-block-15 · gemini-cli-project · savagepad |
| `ideal_output` | string | thinking + scratchpad + final answer, full text |
| `ground_truth` | string \| null | exact answer, for verifiable tier only |
| `rubric` | string \| null | grading criteria, for open tier only |
| `expected_ctl` | `{fires: [], suppresses: []}` | which conditional tags should and should not appear |
| `difficulty_rationale` | string | one line, why this example sits in this tier |

## 04 — Sourcing Pipeline

Three automated passes, zero manual labeling. You review the aggregate pass-rate at the end, not individual rows.

**1 — Seed the verifiable slice from existing benchmarks.**
Pull a subset of GSM8K/MATH for math, HumanEval/MBPP for code, TriviaQA/HotpotQA for factual QA. Ground truth comes free; no labeling cost. This slice anchors the "substantively correct" gate.

**2 — Draft prompts + ideal responses for the open-ended slice.**
For each taxonomy cell without a benchmark source, generate candidate prompts, then generate the ideal formatted response in a separate pass. Two passes, not one — a single call that writes both tends to write a prompt that's suspiciously easy for its own answer.

**3 — Automated grading and filtering.**
Structural parser first (cheap, deterministic, kills malformed output). Then a grader pass — exact-match for verifiable tier, a rubric-scored judge call for open tier — checks the four fidelity gates above. Anything failing any gate is dropped or sent back to step 2, not hand-fixed.

## 05 — Local Model Roster

Ollama on an 8GB RTX 3070. Q4_K_M is the realistic default quant for local pulls. Budgeting ~6.5–7GB usable after driver/context overhead:

| Model | Params | Est. VRAM | Local fit | Notes |
|-------|-------:|----------:|-----------|-------|
| Llama 3.2 Instruct | 3B | ~2.0 GB | fits | fast iteration / baseline floor |
| Phi-3.5-mini | 3.8B | ~2.2 GB | fits | cheap, quick sanity checks |
| Mistral Instruct v0.3 | 7B | ~4.1 GB | fits | plain instruct baseline |
| Qwen2.5 Instruct | 7B | ~4.7 GB | fits | strong instruction-following |
| Llama 3.1 Instruct | 8B | ~4.9 GB | fits | current general-purpose default |
| DeepSeek-R1-Distill-Qwen | 7B | ~4.7 GB | fits | already reasoning-tuned — best contrast case |
| Gemma 2 Instruct | 9B | ~5.5 GB | tight | shrink context window to stay under budget |
| Qwen2.5 / Phi-4 | 14B | ~9 GB | won't fit | spills to CPU offload — slow, skip locally |
| Anything 30B+ | 30B+ | — | won't fit | cloud only — OpenRouter / Together / Fireworks |

> Draw the line between *evaluating* and *training* here. Inference on the six models above is comfortable on a 3070. Actually running LoRA/QLoRA weight updates on anything 7B+ is borderline even quantized — gradients and optimizer state eat the headroom inference doesn't need. Keep the 3070 doing what it's good at: the unattended eval loop below. Rent a spot 3090/4090/A10 (RunPod, Vast.ai) or use a hosted fine-tune API for the actual training runs.

## 06 — Eval Loop

This is what actually runs unattended on the desktop: for each model in the roster, for each held-out task, query via the Ollama API, run the output through the structural parser, run it through the appropriate grader (exact-match or judge call), and log the result. Sequential 7–8B inference is fast enough to clear a few hundred held-out tasks across six models overnight without anyone watching it.

Output is one row per (model × task): compliance pass/fail, substantive-correctness pass/fail, and which CTL tags fired versus expected. Aggregate to a compliance percentage and a fidelity score per model — that's the number that tells you whether native training is worth pursuing at all before you spend a cloud GPU rental on it.

## 07 — Open Questions

Decide these before building the loop.

- Target size for the training set — a few hundred examples is enough to test the concept; a few thousand is what you'd actually want before judging a model "trained."
- Single target format variant, or format-conditioned (same question, different target skeleton depending on a directive)? The schema above already supports the second, cheaper to start with the first.
- Who plays judge for the open-ended rubric grades — a local model, or a cheap hosted call reserved just for grading? Using one of the roster models to grade itself is worth avoiding.
- Where does the trivial-tier negative data come from — hand-written, or filtered down from an existing instruction-tuning dataset?
